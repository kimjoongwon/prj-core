# Orch Delivery

현재 이 skill을 적용한 Codex를 실행의 루트로 취급한다. 이 skill 자체나 별도의 `orch-delivery` custom agent를 실행 주체로 가정하지 않는다.

## 책임

- route/page 요구사항과 기존 구현 근거를 조사한다.
- 구현 전에 spec의 제품 결정과 실행 원장을 확정하고 사용자 승인을 받는다.
- 승인된 원장에서 실행 가능한 단계를 계산한다.
- 각 단계를 해당 custom agent에 직접 위임하고 결과를 수집한다.
- worker의 최종 메시지와 실제 검증 근거를 확인해 원장을 갱신한다.
- 계약 변경이 필요하면 실행을 멈추고 spec을 다시 승인받는다.

제품 구현은 담당 worker가 소유한다. 루트는 owner 산출물을 대신 구현하지 않는다.

## 공식 기능 경계

- Skill은 Codex가 따르는 지침이며 독립 실행 프로세스가 아니다.
- Custom agent와 skill의 연결은 `developer_instructions`와 작업 메시지로 지시한다.
- Subagent 입력과 결과는 자유 형식 텍스트 메시지다.
- Codex 런타임 상태와 프로젝트 작업 결과를 분리한다.
- 실행 원장은 저장소의 프로젝트 계약이며 Codex 내부 상태 머신으로 간주하지 않는다.
- 수정 범위는 책임 경계이며 sandbox 수준의 접근 제어로 간주하지 않는다.

## 실행 원장

Route/page spec에는 다음 표를 하나만 둔다.

| 단계 | owner | 목표 | 입력과 근거 | 수정 범위 | 산출물 | 선행 단계 | 완료 기준 | 작업 상태 | 검증 근거 |
|---|---|---|---|---|---|---|---|---|---|

작업 상태는 `대기`, `실행 중`, `완료`, `입력 필요`, `검증 실패`, `실행 오류`만 사용한다.

- 모든 선행 단계가 `완료`인 `대기` 단계만 실행한다.
- 수정 범위가 겹치는 단계는 선행 관계로 직렬화한다.
- 상태와 검증 근거만 재승인 없이 갱신한다.
- 목표, owner, 입력, 수정 범위, 산출물, 선행 단계 또는 완료 기준을 바꾸면 재승인받는다.
- 예상하지 못한 owner 작업은 임의로 추가 실행하지 말고 원장에 단계를 추가해 재승인받는다.

## Worker 작업 메시지

적용할 skill 이름과 경로를 명시하고 다음 형식으로 전달한다. 실행 문맥은 오케스트레이션에서만 추가한다.

```markdown
## 목표
구현해야 할 단위 작업

## 입력과 근거
모델, spec, 선행 산출물 경로

## 수정 범위
변경 책임 범위

## 기대 산출물
생성하거나 수정해야 할 결과

## 추가 완료 기준
담당 skill의 기본 검증 외 조건

## 실행 문맥
단계, spec 위치, 이전 시도 결과
```

원장 전체를 복사하지 말고 해당 단계 수행에 필요한 근거만 전달한다.

## 실행 절차

1. 관련 요구사항, 코드, spec과 owner 문서를 확인한다.
2. 제품 결정과 단계 계약을 단일 실행 원장에 작성한다.
3. 사용자 승인을 받기 전에는 worker 구현을 시작하지 않는다.
4. 선행 단계와 수정 범위를 기준으로 실행 가능한 단계를 고른다.
5. 서로 독립적인 단계만 동시 실행하고 설정된 동시 실행 한도를 지킨다.
6. 각 worker 작업 메시지에 적용할 builder skill을 명시한다.
7. worker가 끝나면 런타임 상태와 최종 Markdown 보고를 모두 확인한다.
8. 실제 산출물과 검증 근거가 완료 기준을 만족할 때만 `완료`로 기록한다.
9. 완료된 단계에 의존하는 다음 단계를 새로 계산한다.
10. 모든 단계가 완료되면 전체 acceptance를 확인하고 사용자에게 결과를 보고한다.

## Worker 결과 판정

Worker 최종 메시지는 `작업 결과`, `작업 요약`, `변경 산출물`, `수행한 검증`, `남은 문제` 섹션을 사용한다.

`완료` 보고는 실제 산출물과 검증 근거가 모두 있을 때만 승인한다.

`입력 필요` 보고는 구현 전 필수 입력 검사에서 코드 변경 없이 종료한 경우에만 인정한다. 필요한 입력이 기존 승인 원장의 선행 단계라면 해당 단계를 먼저 완료한다. 새 단계나 제품 결정이 필요하면 spec을 다시 승인받는다.

`검증 실패` 보고는 하위 단계를 열지 않는다. 같은 단계와 owner에 이전 결과와 남은 완료 기준을 포함해 재작업을 요청한다.

런타임 `Errored`, `Interrupted`, `Shutdown`은 `실행 오류`로 기록한다. Subagent가 런타임상 `Completed`여도 최종 메시지가 `입력 필요` 또는 `검증 실패`이면 프로젝트 단계는 완료가 아니다.

## 재개

- 검증 근거가 있는 `완료` 단계는 다시 실행하지 않는다.
- 중단된 `실행 중` 단계는 실제 산출물과 subagent 상태를 확인한 뒤 `실행 오류` 또는 `대기`로 정리한다.
- 선행 단계가 완료된 미완료 단계부터 다시 실행한다.
- 원장과 실제 저장소가 다르면 실행 전에 계약을 다시 확인한다.

## 최종 보고

- 완료한 단계와 핵심 산출물
- 단계별 검증 결과
- 실행하지 못한 단계와 이유
- spec 계약 변경 여부
- 남아 있는 위험
