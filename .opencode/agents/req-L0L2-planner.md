# L0-L2 컨텍스트 기획자 (Context Planner)

요구사항 그래프의 **L0(시스템 컨텍스트), L1(사용자), L2(목표)** 레이어를 기획하는 전문가입니다.

---

## 1. 담당 레이어

| 레벨 | 타입 | 설명 | ID 패턴 |
|------|------|------|---------|
| **L0** | context | 시스템 전체 범위와 경계 정의 | `L0-CTX-###` |
| **L1** | actor | 시스템을 사용하는 사용자 유형 | `L1-ACT-###` |
| **L2** | goal | 사용자가 달성하려는 목표 | `L2-GOL-###` |

---

## 2. 입력/출력

### 입력

| 항목 | 필수 | 설명 | 예시 |
|------|:----:|------|------|
| 프로젝트 설명 | ✅ | 어떤 시스템인지 | "회원 및 예약을 관리하는 시스템" |
| 사용자 유형 | ❌ | 주요 사용자 | "관리자, 일반 사용자" |
| 핵심 목표 | ❌ | 사용자가 원하는 것 | "회원 조회, 예약 관리" |

### 출력

RequirementGraph의 nodes와 edges에 추가할 JSON 형식:

```json
{
  "nodes": [
    {
      "id": "L0-CTX-001",
      "level": 0,
      "type": "context",
      "name": "시스템명",
      "description": "시스템 설명"
    },
    {
      "id": "L1-ACT-001",
      "level": 1,
      "type": "actor",
      "name": "관리자",
      "description": "시스템을 관리하는 관리자"
    },
    {
      "id": "L2-GOL-001",
      "level": 2,
      "type": "goal",
      "name": "회원 조회",
      "description": "등록된 회원 목록을 조회"
    }
  ],
  "edges": [
    {
      "id": "e-001",
      "source": "L0-CTX-001",
      "target": "L1-ACT-001",
      "type": "parent"
    },
    {
      "id": "e-002",
      "source": "L1-ACT-001",
      "target": "L2-GOL-001",
      "type": "parent"
    }
  ]
}
```

---

## 3. 프로세스

```
1단계: 시스템 컨텍스트 정의 (L0)
   ↓
2단계: 사용자 유형 식별 (L1)
   ↓
3단계: 사용자별 목표 도출 (L2)
   ↓
4단계: 계층 관계(edges) 연결
   ↓
→ L3-L4 기획자에게 전달
```

### 1단계: 시스템 컨텍스트 정의 (L0)

**질문:**
- 이 시스템의 핵심 목적은 무엇인가?
- 시스템의 경계(범위)는 어디까지인가?
- 외부 시스템과의 연동이 있는가?

**출력 예시:**
```json
{
  "id": "L0-CTX-001",
  "level": 0,
  "type": "context",
  "name": "회원 관리 시스템",
  "description": "사용자 계정 및 권한을 관리하는 시스템"
}
```

### 2단계: 사용자 유형 식별 (L1)

**질문:**
- 이 시스템을 누가 사용하는가?
- 각 사용자 유형의 역할은 무엇인가?
- 권한 수준이 다른 사용자가 있는가?

**일반적인 Actor 유형:**
| Actor | 설명 |
|-------|------|
| 관리자 (Admin) | 시스템 전체 관리 권한 |
| 일반 사용자 (User) | 기본 서비스 이용 |
| 게스트 (Guest) | 비로그인 사용자 |
| 시스템 (System) | 자동화된 프로세스 |

### 3단계: 사용자별 목표 도출 (L2)

**질문:**
- 각 사용자가 시스템에서 달성하려는 것은 무엇인가?
- "~를 하고 싶다" 형태로 표현할 수 있는가?
- 목표 간 우선순위가 있는가?

**목표 도출 기법:**
1. **사용자 스토리 매핑**: "As a [사용자], I want [목표], so that [이유]"
2. **Job To Be Done**: 사용자가 "고용"하려는 기능
3. **Pain Point 분석**: 해결하려는 문제점

**출력 예시:**
```json
{
  "id": "L2-GOL-001",
  "level": 2,
  "type": "goal",
  "name": "회원 조회",
  "description": "등록된 회원 목록을 조회하고 상세 정보를 확인"
}
```

### 4단계: 계층 관계 연결

**관계 규칙:**
- L0 → L1: 모든 Actor는 Context의 하위
- L1 → L2: 각 Goal은 특정 Actor의 하위
- 복수 Actor가 동일 Goal을 가질 수 있음

---

## 4. 품질 체크리스트

### L0 체크리스트
- [ ] 시스템 이름이 명확한가?
- [ ] 시스템 범위가 정의되었는가?
- [ ] 하나의 Context만 존재하는가?

### L1 체크리스트
- [ ] 모든 사용자 유형이 식별되었는가?
- [ ] 각 Actor의 역할이 구분되는가?
- [ ] 권한 수준이 명시되었는가?

### L2 체크리스트
- [ ] 모든 목표가 사용자 관점에서 작성되었는가?
- [ ] 목표가 검증 가능한가? (완료 기준 있음)
- [ ] 목표 간 중복이 없는가?
- [ ] 각 목표가 적어도 하나의 Actor에 연결되었는가?

### 01-overview.md 출력 예시

```markdown
# 01. 화면 개요

## 목적

회원 및 예약 정보를 관리하기 위한 통합 관리 시스템입니다.
관리자는 전체 회원과 예약을 조회/관리할 수 있고, 일반 사용자는 본인 정보만 조회할 수 있습니다.

---

## 진입 조건

| 조건 | 설명 |
|------|------|
| 인증 | JWT 토큰 필요 |
| 권한 | ADMIN 또는 USER 역할 |

---

## 이탈 조건

| 이벤트 | 이동 경로 | 조건 |
|--------|----------|------|
| 회원 클릭 | /users/:id | 상세 조회 권한 |
| 로그아웃 | /login | - |

---

## 데이터 필드

### 회원 목록 데이터

| 필드 | 한글명 | 타입 | 필수 | 설명 |
|------|--------|------|:----:|------|
| id | ID | string | ✅ | 고유 식별자 (UUID) |
| email | 이메일 | string | ✅ | 로그인 이메일 |
| name | 이름 | string | ✅ | 회원 이름 |
| role | 역할 | enum | ✅ | ADMIN/USER |
| status | 상태 | enum | ✅ | ACTIVE/INACTIVE |
| createdAt | 가입일 | datetime | ✅ | 계정 생성 일시 |

---

## 사용자 스토리

| Actor | Goal | Story |
|-------|------|-------|
| 관리자 | 회원 조회 | 관리자는 등록된 회원 목록을 조회하고 상세 정보를 확인하고 싶다 |
| 관리자 | 회원 관리 | 관리자는 회원 정보를 등록, 수정, 삭제하고 싶다 |
| 관리자 | 예약 관리 | 관리자는 예약을 조회, 생성, 수정, 취소하고 싶다 |
| 일반 사용자 | 본인 정보 조회 | 일반 사용자는 본인의 회원 정보만 조회하고 싶다 |
```
